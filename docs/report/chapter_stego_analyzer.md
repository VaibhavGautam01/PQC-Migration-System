# Chapter: The Stego Analyzer

This chapter describes what the Stego Analyzer does, how it was tested, and where it stops. Every number below comes
from a command in this repository. All quantum results come from the Aer simulator at toy size.

## 1. What it is

Sir asked for a tool that takes a stego image as input, breaks it, and then runs the full pipeline. The Analyzer does
this for images made by our own image project. It works out how the message was hidden, extracts it, identifies the
cipher, breaks it where a method applies, gives a labelled estimate where it cannot, and scores the result with the
same risk engine as the rest of the project (weights v1.0). Sir agreed this flow on 22 October 2026. On 27 October
2026 he also accepted the limits in section 5 and the use of the public key as a second input.

## 2. How it works

| # | Stage | What it does | Where |
|---|---|---|---|
| 1 | Accept | reads the image, records its SHA-256 | stego_analyzer/pipeline.py |
| 2 | Detect | tries the pinned image project's own extractor; "lsb" if it returns a hex payload, otherwise "clean or unknown" | detect_method.py |
| 3 | Extract | calls the pinned project's extract_lsb by path; the pinned repository is never edited | extract.py |
| 4 | Identify | textbook RSA (needs the public key), ML-KEM + AES-GCM (by length), or unrecognised | cipher_identify.py |
| 5 | Route | toy key to the Shor circuit, mid-size key to the small-key attack, larger key to an estimate, ML-KEM to "resists" | pipeline.py |
| 6 | Break or estimate | gate-level Shor circuit on the simulator; or the estimate | quantum_stage.py, estimate.py |
| 7 | Score and report | score from src/risk_score.py; JSON, CSV and PDF report | pipeline.py, schema.py, report.py |

The image does not carry the RSA modulus: in our toy format it holds only the hex ciphertext blocks, and the block
width is the same for N = 15, 21 and 35. The attacker in our model holds the stego image and the public key, so the
Analyzer takes the public key (N, e) as a second input (`--public-key N,E`, or two fields on the dashboard page).
Without it the Analyzer does not attack an RSA payload; it says the modulus is unknown and never guesses it.

The Shor stage passes the modulus from the public key to the gate-level circuit (2n+3 qubits, src/q2_shor.py). It
factors nothing with ordinary code first. It chooses a base coprime to N, reads the factors the circuit measured,
rebuilds the private exponent and decrypts. Every run is saved as an evidence record (rule 4) whether or not it found
factors. The static guard (src/quantum_guard.py) scans this module.

## 3. Result states

| State | Meaning |
|---|---|
| broken (toy) | the Shor circuit measured a period, N was factored, the message was decrypted; label "Aer simulator, toy size" |
| broken (classical, small key) | the existing small-key attack succeeded (stage not built, see section 5) |
| vulnerable (estimate) | a Shor-class algorithm but the key is too large to run here; 2n+3 logical qubits and the published figure, labelled ESTIMATE, never a time |
| resists | ML-KEM + AES-GCM payload: extraction works, there is nothing to factor |
| unrecognised | the hiding method or cipher is not in our formats; no guess is made |

## 4. Results

The test set is generated by scripts/make_analyzer_testset.py from the pinned image project, and measured by
scripts/analyzer_testset_run.py. It has 6 images: toy RSA for N = 15, 21 and 35 with the public key, the N = 15
image without the key, one ML-KEM-768 + AES-256-GCM image, and one clean cover.

| Image | Expected | Result |
|---|---|---|
| toy RSA, N = 15, with key | broken (toy) | broken (toy) |
| toy RSA, N = 21, with key | broken (toy) | broken (toy) |
| toy RSA, N = 35, with key | broken (toy) | broken (toy) |
| toy RSA, N = 15, without key | unrecognised | unrecognised |
| ML-KEM + AES-GCM | resists | resists |
| clean cover | unrecognised | unrecognised |

Hiding method, cipher, final state and recovered message were each correct for 100 percent of the images, and the
score equalled the engine's score for the same configuration in 100 percent of the cases. This was run on a fresh
clone of main. Each broken image gave back the hidden message.

The Shor stage uses the same gate-level circuit as the Quantum Lab: for N = 15, 21 and 35 it uses 11, 13 and 15
qubits, and the saved Q2 runs found factors in 60, 80 and 85 percent of 20 shots. Scores from the engine: textbook
RSA with a 256-bit key and keyless embedding 91.9 (Critical), RSA-2048 with OAEP 50.8 (High), ML-KEM-768 +
AES-256-GCM 4.7 (Low). For a 2048-bit key the estimate is 4,099 logical qubits (2n+3); the published figure for
RSA-2048 is marked as an estimate wherever it appears.

## 5. Scope and limits

What it covers: the plain LSB format of our image project, read by the pinned extractor; textbook RSA with a toy key
(N up to 35) when the public key is given; ML-KEM + AES-GCM payloads, recognised by length only.

What it does not cover, and says so:

- RSA-1024 and RSA-2048 are not broken; they get an estimate, never a time.
- The small-key attack for mid-size moduli is not built: the pinned message layout for a non-toy modulus is not known
  to this project.
- OAEP-style blobs are not identified: one OAEP block looks like one textbook block, so it is reported as
  unrecognised rather than guessed.
- The image project's R-channel module and the video project's formats (including XOR-LSB, which belongs to the
  video project) are reported as unrecognised. Sir has not said whether they must be covered. The video project has
  its own attack scripts, which are not part of this Analyzer.
- The detector recognises our own format by trial extraction. It is not general steganalysis and claims no
  confidence.
- ML-KEM recognition uses the payload length only; the structure cannot be checked without the secret key.

The test set is small (6 images), was made by the same team that built the Analyzer, and says nothing about images
from other tools. Accuracy on other tools' images is unknown. The score is a weighted score, not a probability.

## 6. How to run it

    python scripts/make_analyzer_testset.py                   # generate the 6 test images (needs the pinned project)
    python scripts/analyzer_testset_run.py                    # run all of them and print the table
    python run_pipeline.py --input IMAGE.png --public-key 15,3
    streamlit run src/live_dashboard.py                       # page "Stego Analyzer": upload, stages, evidence, downloads

Live runs write their evidence records to outputs/tmp_quantum_runs_analyzer.json, which git ignores. Running
`python scripts/analyzer_testset_run.py --save-evidence` writes them to data/quantum_runs.json instead.
